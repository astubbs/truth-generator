# Releasing

`truth-generator` publishes to **Maven Central** via the [Sonatype Central Portal](https://central.sonatype.com).
Group id: **`bz.stub.truth`** (the `stub.bz` domain, reversed).

## How publishing works

- **`.github/workflows/ci.yml`** ("CI") lints and runs the JDK 17/21 test matrix on every push and PR. It does **not** publish.
- **`.github/workflows/publish.yml`** ("Publish") runs after CI succeeds on `master`. The **version in `pom.xml` is the source of truth**:
  - version ends in `-SNAPSHOT` -> a snapshot is published to the Central Portal snapshot repository.
  - version has no `-SNAPSHOT` -> a release is published to Maven Central, a `v<version>` git tag is created, and the release-drafter draft is published as the GitHub release.
- Publishing uses the `maven-central` profile in `pom.xml` (GPG signing + `central-publishing-maven-plugin`, which bundles, validates, and auto-publishes via the Portal API).

`publish.yml` triggers via `workflow_run` against the **default branch**, so it only takes effect once it is merged to `master`.

## One-time setup (maintainer)

Do this once. All of it is external to the repo; only a maintainer with the accounts/domain can do it.

### 1. Sonatype Central Portal account + namespace

1. Sign in at https://central.sonatype.com (log in with GitHub).
2. Go to **Namespaces** -> **Add Namespace** and register **`bz.stub`**.
3. Central shows a verification key. Add it as a **DNS `TXT` record on `stub.bz`**:
   - Host/name: `@` (the apex `stub.bz`)
   - Value: the verification key Central gives you
4. Back in Central, click **Verify**. Once verified, you can publish any artifact under `bz.stub.*` (so `bz.stub.truth` is covered).
5. (Optional, for snapshots) enable **SNAPSHOT** publishing for the namespace under Publishing settings.
6. Generate a **user token**: account menu -> **Generate User Token**. Save the username/password pair - these become the `MAVEN_CENTRAL_*` secrets.

### 2. GPG signing key

Central requires every artifact to be GPG-signed and the public key to be discoverable on a public keyserver.

```sh
# Generate a key (RSA 4096, no expiry or a long one). Note the passphrase you set.
gpg --full-generate-key

# Find the key id (the long hex after "sec   rsa4096/").
gpg --list-secret-keys --keyid-format=long

# Publish the PUBLIC key so Central can verify signatures.
gpg --keyserver keyserver.ubuntu.com --send-keys <KEYID>

# Export the ARMORED PRIVATE key for CI (this is the MAVEN_GPG_PRIVATE_KEY secret).
gpg --export-secret-keys --armor <KEYID>
```

### 3. GitHub repository secrets

Add these under **Settings -> Secrets and variables -> Actions**:

| Secret | Value |
| --- | --- |
| `MAVEN_CENTRAL_USERNAME` | Central Portal user token username |
| `MAVEN_CENTRAL_PASSWORD` | Central Portal user token password |
| `MAVEN_GPG_PRIVATE_KEY` | Full armored private key from `gpg --export-secret-keys --armor` (including the `-----BEGIN/END-----` lines) |
| `MAVEN_GPG_PASSPHRASE` | The passphrase for that key |

## Cutting a release

1. Open a PR that **strips `-SNAPSHOT`** from `<version>` in the root `pom.xml` (e.g. `0.1.2-SNAPSHOT` -> `0.1.2`). Label/title it per the change (see below).
2. Merge it. CI runs, then Publish deploys `0.1.2` to Maven Central, tags `v0.1.2`, and publishes the GitHub release notes.
3. Open a follow-up PR bumping to the next snapshot (e.g. `0.1.3-SNAPSHOT`) so `master` is back on a development version.

### Release notes

Release notes are generated by [release-drafter](.github/release-drafter.yml) from merged-PR titles, grouped by label:

- `breaking` -> **Breaking Changes** (rendered first) and bumps the resolved minor version (pre-1.0 convention).
- `feature`/`enhancement`, `fix`/`bugfix`/`bug`, `chore`, `build`/`ide` -> their respective sections.

**Label any PR that changes published coordinates or breaks consumers `breaking`**, and state the migration in the PR body, so it lands prominently in the next release's notes.

## Publishing the relocation stubs (optional, one-time)

`relocation/` is a small, self-contained project (not part of the main reactor) that publishes
[relocation POMs](https://maven.apache.org/guides/mini/guide-relocation.html) under the **old** `io.stubbs.truth`
coordinates, redirecting anyone who resolves them to the new `bz.stub.truth` artifacts. It is optional - it only
helps consumers who still reference the old coordinates.

**Prerequisite:** the `io.stubbs` namespace must be verified on the Central Portal (domain verification of
`stubbs.io`), the same way `bz.stub` is verified for the main artifacts. Without it, Central will reject the upload.

Once that namespace is verified (and the same GPG secrets are available locally):

```sh
cd relocation
mvn -B clean deploy \
  -DskipTests \
  -Dgpg.passphrase="$MAVEN_GPG_PASSPHRASE"
```

Keep the `<version>` in `relocation/pom.xml` in step with the version you are relocating from.

## Known follow-ups (out of scope for the Maven Central switch)

These were surfaced while wiring up publishing but are intentionally not addressed here:

1. **Flaky integration-tests code generation.** `generator-assertions-tests` intermittently fails to compile its
   generated sources (missing `InstantSubject`, `ZoneRulesSubject`, `OptionalSubject`, etc.). The identical build
   passes on one run and fails the next, on committed code too - so it is a pre-existing non-determinism in the
   generator (likely reflection-scan ordering), not related to the coordinate change. It can make CI flaky.
2. **Relocation stubs need the `io.stubbs` namespace.** See above - publishing them is blocked on verifying
   `stubbs.io` on the Central Portal. Skip the stubs if that namespace is not available.
3. **Broken javadoc `@see` tags.** `generator-api` has `@see` tags pointing at classes in the core module
   (e.g. `@see MiddleClass in core module`) that cannot resolve. Release javadoc works because doclint is disabled
   (`<doclint>none</doclint>`); the tags themselves could be cleaned up into plain prose separately.
